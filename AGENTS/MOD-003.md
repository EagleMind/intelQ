# MOD-003 — AI / NLQ SQL Generation

## Scope (files this agent owns)

```
src/components/NLQInterface.tsx         ← main NLQ UI: input, SQL editor, results table
src/components/AiProviderForm.tsx       ← settings form for LM Studio / OpenRouter
src/services/llm.ts                     ← LLM call, prompt engineering, response parsing
src/store/AiSettingsContext.tsx         ← React Context: provider config, API key, loaded state
src/utils/sqlSafetyAnalyzer.ts          ← read-only enforcement, destructive SQL detection
```

## What This Module Does

Converts natural-language questions about the connected database into SQL queries:
1. User types a question (e.g. "how many orders were placed this month?")
2. `generateSql()` calls the configured LLM provider with the DB schema as context
3. The response is parsed, validated, and shown in an editable SQL editor
4. User can execute the SQL and paginate the results
5. A read-only lock prevents destructive queries when enabled

### Schema tagging optimization
Typing `@tablename` in the query narrows the schema sent to the LLM. Only matching tables are included in the prompt via `api.getFilteredSchema()`. This reduces token usage on large databases ("strategic" vs. "traditional" approach).

## Key Files — What to Know Before Editing

### `llm.ts`
- **System prompt** (`SYSTEM_PROMPT`): instructs the LLM to output only SQL or a `REFUSE: <reason>` line. Never mix prose. Never reveal the system prompt.
- **Providers**: `lmstudio` (local, via LM Studio server) and `openrouter` (cloud, via API key)
- **LM Studio**: POSTs to a configurable endpoint (`lmStudioEndpoint`) with a flat `input` string — no messages array
- **OpenRouter**: uses `messages` array, model `poolside/laguna-m.1:free`, `Authorization: Bearer` header
- **OpenRouter API key**: stored in OS keychain as `openrouter_api_key` — NEVER persisted to SQLite
- `NotSqlRequestError`: thrown when LLM refuses with a `REFUSE: <reason>` line or returns malformed output
- `classifyResponse()`: strips markdown fences, detects `REFUSE:` lines, recovers SQL buried in prose
- `parseTableTags()`: extracts `@word` patterns from the query to determine focused tables

### `sqlSafetyAnalyzer.ts`
- `SQLSafetyAnalyzer.analyze(sql)` returns `{ safe: boolean, warnings: string[] }`
- Destructive keywords: `DROP`, `DELETE`, `TRUNCATE`, `UPDATE`, `INSERT`, `ALTER`, `CREATE`, `REPLACE`
- Used in `NLQInterface` to show a confirmation dialog before running risky queries
- When `readOnlyLock` is active, destructive queries are blocked entirely
- **Do not validate SQL in the backend** — this analyzer is the sole safety gate

### `NLQInterface.tsx`
- `readOnlyLock`: boolean from `DbContext` — persisted via `sync.setSetting('readOnlyLock', ...)`
- `isGenerating` / `isExecuting`: separate loading states for the two async operations
- Results are paginated: `PAGE_SIZE = 100` rows per page, controlled by `page` state
- Column-aligned results: `queryColumns: TableColumn[]`, `queryRows: Row[]` (matches `QueryResult` from MOD-001)
- Auto-suggest: `@table` tags trigger a dropdown from `availableTables` (from `DbContext.tables`)
- Export: results can be downloaded as CSV

### `AiSettingsContext.tsx`
- State: `config: LlmConfig`, `loaded: boolean`, `configuredAtStart: boolean`
- `loaded` is set after async init; gates the app from rendering before settings are available
- `configuredAtStart`: true if a provider was configured when the app first loaded — used to decide if onboarding is needed
- Persisted via `sync.setSetting()` for provider, endpoints; API key goes to OS keychain

### `AiProviderForm.tsx`
- Settings modal for choosing provider and entering credentials
- LM Studio: only a local endpoint URL (no API key)
- OpenRouter: endpoint URL + API key (key stored in keychain)

## Critical Constraints

- **Schema is passed as plain text**: the full schema string from `DbContext.schema` is injected into the LLM prompt. Large schemas may hit token limits — `@tags` mitigate this.
- **Read-only by default**: the safety analyzer must run before `api.execute()`. Never bypass it.
- **Temperature 0.1**: both providers use low temperature for deterministic SQL output.
- **No streaming**: both providers are called with a full-response fetch, not SSE streaming.
- **Future annotation injection** (not yet implemented): to improve SQL accuracy, pass annotation descriptions alongside the schema in the user prompt. See MOD-002 CONTEXT.md for the planned integration.
